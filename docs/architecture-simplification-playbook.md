# 基础功能异常难做时的架构诊断与精简指南

## 这份指南解决什么问题

当一个看似基础的功能需要不断加特例、跨很多层改代码、反复修复却仍不稳定时，
不要立刻把问题解释成“实现还不够努力”。先检查这个功能依赖的概念，是否在当前
架构中有清楚、唯一、可持久化、可验证的定义。

核心判据是：

> **一个基础功能如果做起来异常艰难，先怀疑它在当前地基上没有被正确定义，
> 而不是继续在现有路径上堆实现。**

这里的“没有定义”通常不是缺少一个类型名，而是系统无法一致回答某个基础问题，
例如：这个值以什么单位表示、谁拥有它、谁可以修改它、冲突时谁赢、刷新后从哪里
恢复、失败后用户如何接管。

本指南用于诊断和收敛，不等于鼓励重写。目标是找到**最小但正确的地基改动**，
让目标功能和后续同类功能都能沿着一条清楚的路径成立。

---

## 一、先判断：这是架构问题，还是普通实现问题

满足下面任意一条，只说明“值得调查”，还不能直接宣布要重构：

- 一个简单交互需要同时修改多个互不相邻的模块；
- 同一个值在不同界面、服务或存储中有不同单位或不同含义；
- 自动化测试通过，但真实页面仍然失效、回弹或刷新丢失；
- 修一个入口会破坏另一个入口，两个入口都声称自己是权威；
- 新功能只能靠窗口尺寸、DOM 测量、顺序、延时或魔法数字间接推导；
- 保存、撤销、重试或并发操作需要整份对象覆盖；
- 错误被静默吞掉，或者系统拒绝后用户没有恢复路径；
- 每次修复都增加分支，却没有减少旧路径。

先排除更普通的原因：

1. 需求是否仍有关键歧义；
2. 是否只是一个局部 bug、缺失状态或边界条件；
3. 是否受第三方 API、浏览器能力、性能预算或数据质量限制；
4. 是否已经有正确抽象，只是当前调用方没有使用；
5. 验证工具是否制造了假象，例如隐藏页面暂停动画、测试数据与真实数据不同；
6. 操作对象与读取对象是否一致。

只有在拿到“现有模型无法一致表达目标行为”的证据后，才进入架构改造。

## 二、把功能翻译成它依赖的基础事实

不要从组件、接口或数据库字段开始。先用用户语言写一句目标：

> 用户在【入口】对【对象】执行【动作】后，应立即看到【结果】；保存、刷新、撤销、
> 重试和其他入口都应保持同一结果。

然后列出这个行为必须依赖的基础事实：

| 问题 | 要确认的内容 |
| --- | --- |
| 对象是什么 | 是否有稳定身份，还是靠数组下标、显示顺序或 DOM 节点临时指代 |
| 值是什么 | 单位、坐标系、精度、边界和空值语义是否明确 |
| 谁拥有真相 | 客户端、服务端、存储、外部供应商，还是某个共享领域模块 |
| 谁能修改 | 是否只有一个权威写入口，还是多个入口都能覆盖同一事实 |
| 如何读取 | 预览、编辑、导出和代理是否使用同一个解析规则 |
| 冲突谁赢 | 并发、重叠、版本冲突和优先级是否有确定规则 |
| 如何恢复 | 刷新、撤销、重试和幂等是否有明确语义 |
| 失败怎么办 | 用户能否看到原因，并有重试、刷新或人工裁决入口 |

如果某一行只能回答“由页面临时算”“看调用顺序”“几个地方各有一套”，它就是
优先调查的地基缺口。

### “存在”的最低标准

一个基础概念只有同时满足以下条件，才算在架构中真正存在：

- **可命名**：团队能用一个稳定术语讨论它；
- **可表示**：有明确单位、精度、范围和身份；
- **可持久化**：保存与刷新不会改变它的含义；
- **可解析**：所有读取方能得到一致结果；
- **可修改**：有唯一或明确协调的写入规则；
- **可验证**：可以用纯函数测试、领域测试和真实入口观察；
- **可接管**：自动路径拒绝或不确定时，用户仍有可执行出路。

缺一项，功能就可能“代码里有，产品上没有”。

## 三、建立证据，不凭代码观感下结论

### 1. 画出一条真实纵向链路

只追踪目标行为涉及的事实，不先阅读整个系统：

```text
用户动作
  → 界面如何识别对象与计算意图
  → 调用哪个命令
  → 服务端如何读取当前事实
  → 哪个领域规则修改它
  → 如何持久化
  → 预览/刷新/导出如何重新解析
  → 失败如何反馈与恢复
```

在每一段标出：输入、输出、单位、对象身份、writer、版本和错误处理。链路中出现
第二套单位、第二个 writer、第二个赢家规则或整份覆盖时，先停下来验证它是否真有
独立语义；不要因为代码相似就贸然合并，也不要因为文件不同就默认它们互不冲突。

### 2. 记录可复测的基线

基线应直接对应用户痛点，例如：

- 一次操作触达多少层、发出多少次写入；
- 保存后刷新是否保持；
- 连续输入是否全部生效；
- 两个入口是否产生同一结果；
- 预览、导出和持久化是否一致；
- 错误是否可见，用户是否能恢复；
- 改动前后的调用点、writer 或转换次数。

文件行数、导出数和依赖数可以作为风险信号，但不能单独证明架构好坏。大文件不是
根因的同义词，小文件也可能只是把同一混乱分散到了更多地方。

### 3. 主动寻找反证

在决定改地基前，至少尝试推翻一次自己的判断：

- 用真实对象复现，而不是只用测试夹具；
- 核对操作对象与读取对象的 ID；
- 检查浏览器隐藏页、动画时钟、缓存和自动刷新是否影响观测；
- 暂时绕过可疑验证工具，确认现象仍存在；
- 搜索已有共享规则，确认不是调用方绕开了它；
- 对照功能账本和历史记录，确认差异不是刻意保留的语义。

诊断错了时，应修正假设，不为已经写出的方案寻找理由。

## 四、选择最小而正确的地基改动

一个好的地基改动，通常能用一句话说明新增或收敛了哪个基础事实，例如：

- 为一个此前依赖容器比例的行为建立明确的业务坐标；
- 让一个持久事实只剩一个领域写入口；
- 让预览、编辑和导出共用同一个解析器；
- 给临时对象建立稳定身份；
- 把客户端上传结果改为客户端提交意图、服务端读取并修改事实；
- 给拒绝和不确定状态补上可见原因与人工接管入口。

优先选择满足这些条件的方案：

1. 修正的是领域事实，不是某个页面的视觉症状；
2. 改动范围能围绕一条纵向链路闭合；
3. 新路径成立后可以立即删除或封死旧路径；
4. 不同时改变用户行为、存储格式和页面设计；
5. 可以先在纯函数或领域层写下确定行为；
6. 失败状态与迁移状态有明确处理方式；
7. 能用真实入口证明改动，而不只靠静态结构宣称完成。

### 三条常用的收敛原则

#### 一个事实，一个权威定义

同一个业务事实只应有一个权威单位、身份和解析规则。不同页面可以有不同投影，
但不能各自发明事实。

#### 一个事实，一个写入协议

调用方提交“要做什么”，权威层读取当前状态并执行领域命令。避免调用方计算整份
最终状态再覆盖回去；否则版本、并发、撤销和多个入口很容易互相踩踏。

“一个写入口”不是要求所有动作共用一个巨大函数。不同领域命令可以独立，但它们
必须通过同一事实所有者协调，不能各自成为第二份真相。

#### 一个拒绝，一条可执行出路

冲突、非法操作和不确定状态应被区分。每种拒绝都要告诉用户发生了什么，以及接下来
可以刷新重试、修改输入、恢复到哪个状态，或在哪里人工裁决。只有禁止、没有接管的
不变量，会把内部一致性变成用户死锁。

## 五、实施顺序：先立事实，再换路径，最后删旧路

### 第 0 步：保护现场

- 阅读项目规则、功能账本和相邻工作的交接记录；
- 确认目标功能当前状态、不可破坏约束和已知缺口；
- 如果会削弱、替换或删除已登记能力，先列出影响并取得用户明确批准；
- 检查未提交改动、并行会话、运行服务和可能产生费用的任务；
- 记录改动前基线与可重复复现步骤。

### 第 1 步：先定义缺失事实

在共享纯函数或领域层明确单位、身份、边界、优先级和转换规则。先写最小测试，证明
这个概念脱离 UI 也成立。不要从 JSX、按钮或样式开始倒推领域语义。

### 第 2 步：建立权威命令或解析器

让权威层自己读取当前状态、校验前置条件、执行修改并持久化。明确：

- 命令输入表达意图，不上传可由服务端推导的整份结果；
- 一次用户操作对应一次原子提交和一次撤销语义；
- 重试具有幂等规则；
- 冲突、非法和不确定状态分类返回；
- 所有失败都能到达可见反馈和恢复路径。

### 第 3 步：迁移一条完整纵向链路

选一个用户能真实触发的入口，从交互到持久化再到刷新读回全部接通。不要同时迁移
所有页面，也不要先搭一个长期与旧路并存的“新架构空壳”。

### 第 4 步：逐个迁移调用方

为每个旧调用点记录它真正改变的事实。形状相似不等于语义相同；只有确认语义一致
后才共用命令。迁移一个，删除一个旧分支，并持续运行定向测试。

### 第 5 步：关闭旧入口

完成标志不是“新接口已经存在”，而是旧 writer、旧转换、旧状态源和旧豁免已经
消失或被守卫禁止。新旧路径长期并存，只是把架构债换了名字。

### 第 6 步：真实验收

至少验证：

```text
操作 → 可见结果 → 保存 → 刷新 → 结果保持
     → 撤销/重做 → 连续输入 → 冲突/失败 → 用户恢复
```

如果该事实被多个消费者读取，还要验证预览、导出、代理或其他入口得出同一结果。
自动化测试证明规则，真实入口证明产品可用，两者不能互相替代。

### 第 7 步：留下棘轮

用测试或静态边界守卫防止旧模式重新出现，例如禁止新增第二个 writer、重复解析器、
整份覆盖或绕开领域网关的调用。守卫应冻结并逐步降低真实基线，不能为了“全绿”
掩盖已有债务，也不能只靠注释维持。

### 第 8 步：更新账本与交接

记录权威代码、测试证据、真实验收、不可破坏约束、剩余缺口和被删除的旧路径。
日期、行数和调用点属于当时快照，不要写成永久事实。

## 六、拆除旧界面或旧模块前的责任盘点

两个界面看起来都在编辑同一对象，不代表其中一个可以直接删除。旧表面可能偷偷承担
播放时钟、音频、快捷键、缓存刷新、错误提示、权限检查或撤销注册等非视觉职责。

删除前逐项检查：

1. 列出它接收的 props、context 和回调；
2. 搜索哪些职责只在这里被消费；
3. 把必须保留的职责移动到正确所有者；
4. 为迁移后的职责建立测试或真实验证；
5. 删除旧表面，再搜索孤儿引用和重复状态；
6. 验证用户能力，而不只是确认页面能打开。

“只有一个可编辑表面”是可能的结果，不是所有功能都必须遵守的教条。多个表面可以
存在，但它们必须是同一模型的投影，并通过同一个写入协议协作。

## 七、常见的错误做法

### 1. 把难做自动等同于应该重写

重写会同时扩大行为、数据迁移和验收范围。除非现有模型完全无法渐进迁移，否则先做
一个有限的纵向切片，并用结果决定是否继续。

### 2. 只按文件大小拆分

把 300 行移进 helper，可能没有减少任何职责、writer 或转换。衡量是否精简，应看
事实所有权、修改触达面、调用路径和旧代码是否消失。

### 3. 看到重复代码就合并

相似代码可能承载不同的失败语义、权限范围、版本作用域或生命周期。合并前必须证明
它们处理的是同一事实；否则“去重”会抹掉必要区别。

### 4. 新旧路径长期双轨运行

为了安全先加新路径可以接受，但迁移单元结束时必须删掉旧路或明确设置短期到期条件。
没有关闭计划的兼容层通常会成为第三个真相来源。

### 5. 把静态不可达当成可删除

还要检查动态入口、脚本、外部回调、功能账本和真实用户流程。删除已登记能力前必须
获得批准；Git 历史可以恢复代码，但不能恢复被误删的数据和用户信任。

### 6. 测试全绿就宣称完成

测试环境可能冻结动画、绕过浏览器事件、使用理想化数据或漏掉刷新。真实入口的
保存—刷新—恢复链路是架构收敛的必要证据。

### 7. 只保证系统拒绝正确，不保证用户能继续

严格校验、CAS 和唯一写入口都可能正确地拒绝请求。如果用户看不到原因或无法接管，
产品仍然不可用。人工恢复路径是架构的一部分，不是事后补的 UI 文案。

## 九、是否应该动地基的决策门

进入实现前，给下面每项回答“是 / 否 / 未知”：

| 决策问题 | 结论 |
| --- | --- |
| 已用真实入口稳定复现，而不是只凭代码观感 |  |
| 已排除需求歧义、局部 bug 和工具盲区 |  |
| 已找到当前模型无法一致表达目标行为的直接证据 |  |
| 能说清缺失或冲突的是哪个基础事实 |  |
| 能限定一个可闭合的纵向切片 |  |
| 新路径成立后能删除或封死旧路径 |  |
| 已确认不会静默削弱已登记能力 |  |
| 有自动化证据和真实入口验收方案 |  |
| 对拒绝、迁移失败和人工恢复已有设计 |  |

关键项仍是“未知”时，继续调查；关键项为“否”时，优先做局部修复或重新澄清需求。
不要用一个漂亮的架构方案替代缺失的证据。

## 十、完成的定义

架构精简不是“新抽象已经写完”，也不是“文件变小”。一个收敛单元只有同时满足
以下条件才算完成：

- 用户目标在真实入口可完成；
- 基础事实有唯一、清楚的定义和所有者；
- 保存、刷新、撤销、重试与其他读取方保持一致；
- 失败可见且用户有恢复路径；
- 被替代的 writer、转换、状态源和兼容豁免已经删除或被守卫封死；
- 自动化测试、真实验收和功能账本都留下证据；
- 下一次同类改动需要触达的事实和入口更少，而不是多了一层转发。

最有价值的结果不是“这次功能终于做出来了”，而是系统从此拥有了完成这一类功能
所需要的语言、规则和边界。
