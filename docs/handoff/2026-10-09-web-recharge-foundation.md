# 网页充值基础与商户准备

日期：2026-10-09。订单持久化、原子入账与未开放状态入口已随正式版上线，微信联系方式在 e28faeb4 上线；**真实收款尚未开放**。当前自动续费与单次充值开发位于 codex/alipay-web-payment，尚未部署。旧计费工作树已合并，旧文档中的未部署状态不再适用。

## 现在可以验证什么

- 电脑顶栏、账户余额区域和手机“我”页可点击“充值算力”；服务端返回尚未开放及支持邮箱，不显示付款码、不创建付款。
- `computePayment.availability` / `createOrder` 与只读 `computeAccount` 分开；匿名不能访问，普通用户和管理员都不能绕过关闭状态。
- `drizzle/0027_compute_payment_orders.sql` 新增订单表；账本枚举末尾增加 `purchase`，保留旧枚举顺序。生成的 journal / snapshot 已同步。迁移已随充值基础应用生产。
- `server/repositories/computePayments.ts` 的内部创建函数接受服务器确定的金额与算力，使用 `(userId, requestId)` 幂等；订单查询按 userId 限制归属。
- `settleComputePayment` 必须只接收已验签的成功回调或经过认证的查单结果。校验订单、商户、渠道、币种、金额；订单 paid、purchase 流水和余额在同一 MySQL 事务提交。重复渠道交易号触发唯一约束并回滚全部修改。通用账本写入口拒绝 purchase。
- 真实支付不降级到本地 JSON 持久化。尚无外部回调路径、支付 SDK 或商户 API 调用，浏览器不能声明自己已付款。

## 你需要准备的东西

不需要发个人微信或支付宝收款码。系统接入商户 API 后，会为每笔订单生成独立二维码或支付跳转。

1. **选择首个渠道并确认商户资格。** 微信支付：商户号及已开通的支付产品；电脑扫码通常需要 Native 支付，手机网页需根据浏览器环境选择 H5 或 JSAPI，并满足渠道的申请要求。支付宝：商户账号、开放平台应用及已签约的电脑网站/手机网站支付产品。只有个人收款功能不等于开通网站支付 API。
2. **商户资料与结算账户。** 按渠道申请页面准备营业主体资料、管理员身份及结算银行账户；具体准入以渠道审核结果为准。
3. **配置材料。** 微信：mchid、对应 appid、API v3 密钥、商户 API 私钥和证书序列号、平台验签公钥/证书及其标识。支付宝：appId、应用签名私钥、支付宝验签公钥或渠道要求的证书套件。私钥只配置在服务器的受限环境/密钥文件中，不发聊天、不入 Git、不进入前端。
4. **充值规则。** 待确认建议档位：10/30/100 元分别到账 20/60/200 算力，不赠送。付款页必须让用户清楚看到实付金额和到账算力；当前功能卡“普通页面只显示算力”的例外尚待用户确认，代码未加入价格展示。
5. **退款与发票安排。** 确定支持联系方式、退款条件及开票方式。账本 adjustment 只调整算力，不等于向用户退钱；现金退款需要渠道退款 API、独立退款记录和防重复处理。

正式域名现为 `https://www.drinkingtime.top`；商户后台域名、HTTPS 通知地址及所需备案/审核按所选产品配置，回调路径待适配器确定。

## 接下来从哪里接

1. 服务层定义服务器端批准的 offer 列表。客户端只传 offerId 和幂等 requestId；userId 来自会话，不接收自报金额/算力/付款成功。
2. 服务端创建订单后调用渠道；超时视为提交结果未知，重试/查单使用原订单号，不新建重复付款。网络请求不放进账本事务锁内。
3. 实现渠道适配器：请求签名、响应验签、回调验签及必要的解密，验证成功支付状态与商户/appId。调用内部 `settleComputePayment` 前完成这些检查，不能把 schema 校验当作签名校验。
4. 回调在 `server/_core/index.ts` 的 JSON parser 和通用 origin 检查之前注册精确路径；仅该路径采用渠道认证，保留原始 body 验签，不能放宽一般 API 的保护。
5. 挂接当前用户的订单状态查询与渠道主动查单补偿；明确超时、关单、迟到成功和退款状态。当前表仅 pending/paid，还没有过期/关单及补偿任务。
6. 扩展 `RechargeDialog.tsx` 的档位、支付展示、等待/失败/成功状态；以服务端 paid 为准刷新 balance/statement，切账号清除订单展示。补余额不足错误里的入口。当前只有未开放状态。
7. 接入渠道测试后验证错误签名、金额/商户/appId/币种不匹配、重复和乱序回调、回调丢失查单、跨账号访问，再完成获授权的小额真实支付与退款验收。当前不宣称收款链路可用。

- 用户明确要求支付宝自动续费，而非每月手动买一次；没有用完的算力自动结转下个月。

- 仅充值/订阅交易界面展示人民币价格，工作区仍只显示算力。
- 用户新增独立的单次充值服务；单次充值价格仍待答复，不沿用未确认建议，更不能因此创建自动续费协议。
- 旧文档 10/30/100 元建议不是订阅档位。订阅与单次充值共享原账号账本，不迁移或清空原余额。

### 接入范围与未完成项

当前代码只添加服务端批准的订阅目录、充值弹窗两类服务及待开放说明，createOrder 继续拒绝所有下单。没有签约、代扣任务或自动开通功能，也未部署。

支付宝电脑网站支付已签约，不代表周期扣款/自动续费产品已获准。商户对话负责核实产品名称、适用业务、申请入口和资质；应用 AppID、签名配置、企业限制及备案仍需解决。不得将电脑网站支付或静态转账码包装成自动续费。

后续完整实现须包含：

1. 服务端绑定 userId、不可变套餐版本与支付宝协议号，验证签约、解约通知；浏览器回跳不作为授权生效或到账依据。
2. 每次周期账单唯一键、固定报价快照、订单与渠道交易号幂等；签约本身不发算力，只有核实付款成功才到账。
3. 自动扣款前按产品要求通知用户；超时先查原单、不重新扣同一期；后台重启、多实例与重复通知不重复扣款或入账。
4. 用户可查看下期日期/金额、取消自动续费；外部解约同步停止未来扣款。取消与在途订单竞态须查单处理，不清空原算力。
5. 结转采用原账本余额累加，无月末清零任务。退款、换档、多订阅叠加、续费失败重试和取消后的具体条款须在上线前明确。
6. 月周期起算日、月末对齐和扣款时间按最终获准产品约束制定，签约前明确展示；不要把自然月、30天或自动代扣日期猜成已批准规则。
7. 分别验证签约未付款、重复周期扣款、错账号/错协议/错金额、回调丢失、解约和月末边界；完成获授权的真实签约、续费及取消验收后才能启用。
