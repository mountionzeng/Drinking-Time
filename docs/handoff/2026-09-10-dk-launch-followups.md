## 已确认的产品目标

**角色正式名称：聊聊。** 用户已认可首版视觉方向，并纠正角色称呼。所有面向用户的名称、辅助说明与无障碍标签统一使用“聊聊”；设计稿中的旧称“小杯子”需在实现时替换，输入提示可用“和聊聊说说…”。五种外形都属于聊聊，外形变化不改变名称。现有 PNG 尚未重绘，不能照抄其中旧称。

**现有手机版本做到什么程度，微信小程序版本就应做到什么程度。** 微信版要对齐手机版的用户能力与体验完整度，不能仅以能启动、能登录、能聊天作为完成标准。用户还明确要求补齐电脑版已有的自定义聊天题目能力。

手机端指手机 Web 版本。用户尚不确定上述功能在手机 Web 上的现状，不能将其视为已经实现或验收；微信版最终对标的是本轮完善并经用户验收的手机 Web 版本。具体版本与完整功能清单待后续核对，不凭现有历史待办推断全部需求。这里的“微信小程序版本”表达目标产品形态；当前实际工程仍为小游戏，普通小程序准入与迁移决定仍须核实，不能据此直接迁移。

## 已确认的实施节奏：按完整流程逐项推进两端

手机 Web 与微信的运行环境不同。两端对齐用户能力、交互规则与数据语义；界面、键盘、滚动和动画按环境适配，不假定手机 Web 代码可以直接搬到微信，也不以手机 Web 流畅推断微信流畅。

1. **核对现状与提前验证环境限制**：逐项检查手机 Web 的 R02–R09，区分已满足、需要完善和尚未实现；题目功能核对电脑版现有行为。执行阶段应提前对微信键盘、直接发送、滚动及收起布局做范围受控的技术验证，记录设备、工程类型、可行性与限制。技术验证不等于产品验收，不据此擅自迁移平台或改变产品要求。
2. **先打通一条完整聊天流程**：以“收起聊天 → 输入 → 直接发送 → 聊聊显示思考状态 → 话语框展示回答（保持收起）”为首个流程，先在手机 Web 完善并由用户体验确认，记录验收版本与证据。已明确回答直接显示在聊聊的话语框中，收到回复不自动展开完整聊天；长回答的框内阅读方式仍待细化。
3. **紧接着适配并验收微信同一流程**：以用户确认的手机 Web 体验为基线，在微信环境实现并真机验证；暴露平台限制时及时反馈，不等整套手机功能全部做完才检查微信可行性。
4. **再推进下一项能力或流程**：沿用“手机 Web 核对与完善 → 用户确认 → 微信适配与独立验收”的节奏。题目编辑等其余事项按下方执行阶段推进；可根据核查结果细化技术步骤，不得更改已确认的产品行为。

R02–R09 是两端共同的目标要求。性能和键盘交互分别在真实安卓与 iOS 的手机 Web、微信环境验证；微信截图只能作为微信端问题证据，不能据此断言手机 Web 有相同缺陷。数据与业务规则优先沿用现有权威服务，避免产生两份不一致的数据；共享代码的具体范围由执行前核查决定，不为复用而新增通用框架。

当前实际微信工程为小游戏，普通小程序准入与迁移方向尚未确定。现有 Canvas 交互与原生小程序组件的适配成本不同，须结合预检和技术验证再细化工作量，当前不承诺工期。接手 Agent 应先完成阶段 A 的核查，再进入对应实现。

## 第一批需求：聊天与手机交互

来源：用户本轮描述及两张微信界面截图（`058f23ebc746d27f35bf43b2cbba406e.jpg`、`5a99a1f0904d91fee1d910f48d1d0274.jpg`）。截图展示正文区、聊天面板、聊聊与键盘；键盘上方显示“完成”，页面另有“发送”。卡顿与输入自动展开属于用户报告，本轮未做运行复现，不预判技术根因。

| 编号 | 用户要求 | 验收条件 |
| --- | --- | --- |
| R01 | 微信版对齐现有手机版的完善程度 | 执行前逐项列出手机版已有入口、用户操作及微信版差距，形成对照清单并逐项验证；不得把已有能力直接删减为“以后再做”。平台差异导致无法等效实现时，先说明影响并由用户裁定。完整清单尚待梳理。 |
| R02 | 支持自定义聊天题目，参照电脑版已有功能 | 用户能找到题目编辑入口、输入自己的题目并保存，离开后重新打开仍显示保存结果。实现前核对电脑版“聊天题目”的真实对象与保存行为，不能自行替换成正文标题编辑或仅改展示文案。 |
| R03 | 解决操作明显卡顿 | 覆盖打开聊天、展开/收起、滚动、唤起键盘、输入和发送；记录相同设备与场景下的修改前后表现。输入跟手、点击有反馈、滚动无明显停顿；模型或网络等待与界面响应分开记录，等待回复时界面仍可操作。量化阈值待取得基线后确定，不凭感觉宣称完成。 |
| R04 | 聊天展开时遵循常规聊天界面 | 对话按顺序显示，双方消息清楚可辨，历史可滚动；输入区、消息区与键盘布局协调，最新消息和发送入口可见，不出现截图中消息被截断、控件漂移或相互遮挡的问题。 |
| R05 | 聊天收起后，仍能看到聊聊的交互及它说的话 | 收起完整聊天记录后，聊聊仍可见、可交互，它当前说的话仍可读；不能把收起实现为连同聊聊和话语一起隐藏。聊聊的具体交互沿用现有产品；收起时通过它的话语框直接展示回答，表情状态见 R08，回答展示见 R09。 |
| R06 | 开始打字不能自动展开聊天 | 在收起状态点击输入、唤起键盘、输入和收键盘，聊天均保持收起；展开由用户主动操作。键盘避让不等于展开面板；状态切换不丢草稿。收到回复也保持收起，直接在话语框展示内容，见 R09。 |
| R07 | 输入后可以直接发送，无需先点“完成”再点“发送” | 键盘处提供直接发送动作，一次明确操作即可发出消息；页面发送按钮若保留，也应在键盘打开时直接发送。两种入口都不能重复发送，中文选词确认不能误发，收键盘不能误发或丢草稿；空白消息不发送。先在真实安卓和 iOS 的手机 Web 验收，再在两类设备的微信环境验收。 |
| R08 | 聊聊具备可见的不同表情，明确表现“正在思考” | 用户发送消息后、等待回答期间，聊聊呈现可辨认的思考表情或动作；不能只有普通加载提示而聊聊毫无变化。状态跟随真实请求：回答到达后结束思考，失败或中断后不能一直假装思考。其他表情的种类与视觉样式后续确认，不自行扩展情绪系统。 |
| R09 | 回答直接显示在聊聊的话语框，不展开完整聊天 | 在聊天收起状态发送消息，回答到达后直接显示真实回答内容，不能只显示“有新消息”并要求展开查看。聊聊与话语框保持可见，完整聊天面板保持收起；用户仍可主动展开查看历史。长回答须能在收起状态下读完，具体框内滚动或其他阅读方式待确认，不得把自动展开聊天作为长回答的处理方式。 |

以上是本轮明确需求，不再沿用旧文档“体验增强单独后补”的笼统安排。按完整流程逐项完成手机 Web 验收与微信对齐的节奏已确定；各阶段交付和门槛见下文。

## 实现前需收敛的细节

这些细节不阻塞阶段 A，也不要求重新讨论已确认的产品目标：

- **题目的对象**：先查电脑版真实入口和保存行为；仍存在歧义时，仅对这一点询问用户，再实现 R02。
- **长回答**：建议先做有限高度的话语框并在框内滚动，让用户在阶段 B 体验确认；这是待验证方案，不是用户已经选定的样式。无论采用何种布局，都不能强制展开完整聊天才能读完。
- **聊聊表情**：首个流程先落实正常与思考的可辨区别，回答到达、失败或中断时正确退出思考。优先检查已有素材；其他表情先列候选供用户确认，不自行发明情绪系统。
- **性能**：阶段 A 记录实际设备和复现步骤，再设定可复测指标。将本地输入/滚动延迟与模型等待分开；量化目标需有基线依据，不编造已经达到的帧率或时延。
- **平台**：先读 `docs/handoff/2026-09-10-miniprogram-admission-preflight.md` 并核实工程现状；普通小程序迁移未获决定前，只做现有环境的必要验证与适配，不自行启动迁移。

### 点击“存入故事”后的流程

1. 打开底部选择面板，默认定位当前故事的可编辑版本；用户可切换到本人其他故事，再选择该故事的版本。切换故事重置版本选择，防止拿旧故事的版本身份保存。
2. 点击“下一步：预览正文”，显示明确的目标故事、目标版本、聊聊整理的正文；允许预览修改，返回选择时保留这份草稿。此时还没有写入。
3. **设计建议，未获用户裁定**：默认“追加到末尾”，另一项为“替换该版本正文”。切换方式时显示影响说明；最终按钮对应“确认追加并存入”或“确认替换并存入”。只允许对可编辑版本执行，不能隐式覆盖成品。
4. 真实保存成功后明确显示目标故事和版本；原聊天保留，不自动删除或搬走消息。用户可自行返回聊天或查看目标结果。失败时保留预览稿和目标选择；再次提交不得产生重复追加。

### 已核实的版本约束与待决策冲突

功能卡 `publishing-versions` 为 `observing`，规定：已完成成品不可修改，只有唯一 editing 组合行可更新；保存文字不能改图像/视频，普通保存不能自动建版，使用预期 revision 与幂等 receipt 防止覆盖和重复。`publishing-workspace` 为 `working`，平台稿须隔离，人工标题不得被正文操作清空。

因此设计演示将“已完成”版本列为只读，仅允许选“编辑中”版本。用户所说“之前某个版本”若指已完成成品，与现有约束存在冲突：执行 Agent 应说明差异并等待裁定，不直接放开旧版本覆盖。可提出“从该成品继续到编辑中版本”的方案，但需用户确认及核实已有语义，不能因一次归档自动新建版本。若目标已有更新、被删除、无权限或不存在可编辑版本，保持草稿并说明原因，不静默改存其他位置。
