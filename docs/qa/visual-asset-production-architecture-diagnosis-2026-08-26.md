# 视觉资产制作流程架构诊断

## 1. 用户目标

创作者在 `/editing` 的当前 Story 素材仓库中，把已选图片建立为人物、场景或美术风格资产；系统只按创作者声明的参考职责提取事实。保存、刷新、建新版、镜头绑定、付费生成和查看历史结果后，职责与当时使用的资产版本都保持不变。

## 2. 当前异常与基线

- 资产版本原先只持久化 `referenceImageIds`，能回答“用了哪些图”，不能回答“每张图负责证明什么”。
- 创建界面先选资产类型再勾图，但逐图职责没有进入领域模型、路由或 Story 持久化。
- 分析提示只按整个资产类型隔离人物、场景和风格，无法引用一条可审计的逐图职责事实。
- 本轮开始时没有 dev server；主仓库存在用户未提交的需求、指南和媒体目录，均不修改或清理。

## 3. 已登记能力与红线

- `story-visual-assets`：`observing`。扩展现有 Story 视觉资产聚合，不建立第二套资产、版本或镜头绑定系统。
- `story-ownership`：所有读写同时校验 `storyId + userId`。
- `stable-shot-identity`：正式绑定继续落到 `stableShotId + immutable versionId`。
- `image-asset-history`：生成成功不等于采用；不得静默覆盖当前图片。
- 付费前门禁、未知任务不重提、锁定版本不可原地修改等既有约束保持不变。

## 4. 基础事实表

| 事实 | 当前权威表示 | 权威所有者 | writer | 持久化位置 | 冲突/拒绝 | 恢复路径 |
| --- | --- | --- | --- | --- | --- | --- |
| 资产参考职责 | `VisualAssetReference { imageId, role }` | `shared/visualAssets.ts` | `createVisualAssetDraft` / `createVisualAssetVersion` | `Story.body.visualAssets.assets[].versions[].references` | 职责与资产类型不一致时写入前拒绝 | 修正选择后重提；旧 `referenceImageIds` 读取时迁移 |
| 资产版本 | 不可变 `assetId + versionId` | 现有视觉资产聚合 | 现有 CAS 命令 | Story body | revision 冲突提示刷新 | 刷新后按同一意图重提 |
| 来源图片 | 当前 Story 的 generated image `imageId` | 图片仓库 | 现有导入/生成入口 | generated images | 非本 Story / 非本人 / 不可用时拒绝 | 重新导入或选择有效图片 |

职责词汇在 v1 严格按资产类型收敛：人物 `character-identity`、场景 `scene-space`、风格 `style-language`。它声明该图只证明该资产维度，不赋予构图、其他资产维度或主体布局控制权。

## 5. 第一条纵向链路

选择资产类型与图片 → UI 为每张图显示并提交明确职责 → tRPC 严格校验结构 → Story CAS 命令校验职责与类型、图片归属 → 持久化 `references` → 刷新归一化读回 → 分析输入携带图片 ID 与职责 → 固定事实/冲突继续写回同一不可变版本。

## 6. 架构假设与反证

- 假设：R3/R4 难以稳定实现的根因之一，是“参考职责”没有成为可持久化基础事实。
- 直接证据：生产模型、路由和 UI 只有 `referenceImageIds`；分析服务无法从版本中读取逐图职责。
- 反证检查：现有资产类型已经提供一层隔离，因此不需要建立任意标签系统；v1 只增加类型约束的逐图职责，避免提前发明更细的角色分类。
- 推翻条件：若后续真实制作证明同一资产类型内部还必须区分脸、服装或材质等证据职责，再以真实失败样例扩展枚举；本轮不预设。

## 7. 最小地基改动

- 新增事实：每张资产参考都由 `imageId + role` 唯一表示。
- 权威所有者：现有 `StoryVisualAssets` 聚合和 CAS 写入协议。
- 迁移：schema v2 读取旧 `referenceImageIds` 时按资产类型生成职责；所有新 writer 只接受 `references`。
- 关闭旧路：静态测试禁止路由、持久化、分析和创建 UI 再写 `referenceImageIds`；共享归一化器只保留一个旧数据读取点。
- 明确不改：不改镜头绑定、标准视图、供应商、付费任务、质检与采用语义。

## 8. 拒绝与人工接管

| 失败类型 | 用户/调用方看到什么 | 可执行出路 |
| --- | --- | --- |
| conflict | Story revision 已变化 | 刷新资产聚合后重新提交 |
| invalid | 参考职责与资产类型不一致，或图片不属于当前 Story | 重选资产类型/图片后提交 |
| uncertain | 本切片不产生付费或供应商 unknown | 由后续付费任务切片沿用现有恢复语义 |

## 9. 决策门

| 问题 | 结论 |
| --- | --- |
| 已用真实入口稳定复现 | 未知；当前先有代码链路和账本直接证据，UI 真实验收待主仓库 3000 |
| 已排除局部 bug | 是；缺口同时跨模型、API、持久化、分析和 UI |
| 当前模型无法表达目标行为 | 是；旧版本没有逐图职责字段 |
| 能说清缺失事实 | 是；资产参考职责 |
| 能限定闭合纵向切片 | 是；创建/建新版到分析与刷新读回 |
| 新路径后能封死旧路 | 是；旧字段仅留归一化迁移读取 |
| 不削弱登记能力 | 是；不删除或替换现有资产/绑定/生成能力 |
| 有自动化与真实验收方案 | 是；领域、持久化、路由、UI 测试 + main:3000 创建/刷新 |
| 有拒绝与恢复设计 | 是；类型不匹配拒绝、CAS 刷新重试、旧数据自动读取迁移 |
