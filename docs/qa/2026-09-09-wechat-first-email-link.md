# 微信优先、登录后自愿关联账号

日期：2026-09-09。分支：codex/wechat-mobile-parity。状态：observing，微信优先客户端预览已上传，关联后端尚未部署。

## 用户确认的体验与规则

- 网站与小游戏按使用场景选择主要入口：网站以邮箱登录为主，小游戏以微信登录为主；两端均不要求先关联另一个身份。
- 网站登录后，在「个人信息 → 关联账号」自愿关联微信；小游戏登录后，在「我」自愿关联邮箱或已有账号。关联成功后，两种登录方式进入同一账号、同一份故事和余额。
- 网站现有 AuthEntryPanel 仍为邮箱加内测邀请码入口，MobileAccountPanel 尚未接入微信关联。本条是用户确认的产品规则，不代表网站入口已经实现；本轮未更改网站认证方式。其他平台尚未指定，不展示虚假的可用关联按钮。
- 微信端首屏以「微信登录」为主，「其他方式：邮箱登录」为次要入口。
- 微信登录后可直接新建故事、使用自己的工作区；不强制关联邮箱。
- 「我 → 关联邮箱 / 已有账号」完全自愿；即使还没有故事，也必须有「我」入口。
- 新邮箱验证后绑定当前微信账号，不移动当前内容。
- 已有邮箱账号验证后复用原账号的故事和余额，微信以后仍可直接进入；只允许转移无内容的纯微信身份，不删除源账号。
- 当前微信账号已有故事、出生资料、记忆、账务/权益、凭据或其他身份时停止关联，两边内容不合并、不覆盖。
- 历史邮箱缺身份登记时，不全局自动认领。须逐邮箱人工批准后，仍由本人完成当前微信 code 与邮件验证码双重证明。

## 实现与安全边界

- 入口：minigame/src/liveGame.ts、accountView.ts、workspaceView.ts。
- HTTP：POST /api/minigame/bind/email/otp/request 与 /bind/email；近期独立 Bearer、显式 confirm=true、限流、大小限制，不接收 userId。
- 唯一账号读写入口：server/services/accountIdentity.ts。未新增 server/db.ts 直接导入方，也未改 schema 或迁移。
- 绑定验证码用独立派生摘要绑定 source userId/sessionVersion；用途 verify，与 Web 验证和登录码不可互用。10 分钟、最多 5 次猜测，沿用共享持久化发送/验证限流。
- 事务复查当前微信 subject 所属、会话版本、唯一邮箱归属；身份移动、OTP 消耗、源会话撤销与审计同事务提交，任何写入失败全部回滚。
- 审计保存于 data_migration_receipts（sourceKey=minigame_email_link），只存内部账号/identity/challenge 信息与带密钥摘要，不记明文验证码、微信 subject 或邮箱。
- minigameAccountLock 使用跨进程 MySQL 命名锁，与游戏工作区请求共用；独立短连接避免等待锁占满业务连接池。在途写入完成后再检查源账号；后续请求取得锁后由工作区再次检查会话版本。
- 客户端先 disconnect 两个工作区，再加载新会话内容。晚到响应受 epoch 防护；未保存正文、聊天或新资料草稿不会被绑定动作丢弃。
- MINIGAME_EMAIL_LINK_ENABLED 默认关闭；关闭关联不影响已有独立微信登录。
