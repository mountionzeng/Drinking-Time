# 生成文本提示词整理

整理日期：2026-09-29。本文供单独讨论和调整文字生成提示词；是当前代码的阅读稿，编辑本文不会自动改变运行时。下文明确区分原文摘录、规则摘要和待讨论建议。

## 1. 生效位置

| 任务 | 当前权威位置 | 输入与作用 |
| --- | --- | --- |
| 首次生成正文 | `server/services/publishingDraft.ts` → `compileGeneratePublishingDraftPrompt` | 用户对话、当前平台、写作用途；生成故事内核和一份平台稿 |
| 平台转换 | 同文件 → `compileConvertPublishingDraftPrompt` | 故事内核、来源稿、目标平台；生成目标平台稿 |
| 按要求改写正文 | 同文件 → `compileRevisePublishingDraftPrompt` | 故事内核、当前稿、用户本次要求 |
| 标题写作规则 | 同文件 → `publishingTitleContext` | 首次生成、平台转换、文风修复时拼入 |
| 写作用途与观众 | 同文件 → `narrativeIntentContext` | 首次生成时拼入 |
| 平台文风 | `shared/publishingDraft.ts` → `PUBLISHING_PLATFORM_REGISTRY.copyGuidance` | 由 `platformContext` 拼入多个生成路径 |
| 模型结果结构修复 | `publishingDraft.ts` 中三个 `compile…RepairPrompt` | 仅修复无效候选的结构与必要硬长度 |
| 克制文风修复 | 同文件 → `compileRevisePublishingStyleRepairPrompt` | 检出特定表达后再次调整措辞 |
| 用户点击只修格式 | 同文件 → `repairPublishingDraftFormatting` | 本地处理换行、标签和 X 编号，不使用模型提示词 |

提示词之外还有输入上下文与输出校验；不能只修改一句系统提示词就认为所有生成路径都已改变。

## 2. 首次生成：当前主提示词原文

以下是主提示词固定正文，后面还会拼入第 3～5 节以及 JSON 输出要求。

```text
你是个人发布稿编辑。你的工作是把用户已经说出的想法整理成大众能读懂的文字，同时保留鲜明的个人判断。
这不是批量营销稿：不要削弱批评，不要添加用户没说过的经历、数据或结论，不要把有棱角的话改成空泛鸡汤。
严格保持事实来源身份、时态与确定程度：看到、听说、报道、计划、可能或小样本都不得升级成已确认、已执行、必然发生或普遍结论。事实边界优先于用户要求。
默认写得清楚、直接、有个人判断：不要煽情、装深沉、堆比喻、滥用反问或制造虚假的宏大感；除非用户明确就是这样说话。
优先写具体发生了什么、用户为什么不同意，再写结论。不要用“危险的信号”“背叛”“反噬”“守住……就是守住……”这类宏大措辞代替论证。
保留具体判断，但删除口号感、AI 腔和 Markdown 粗体符号。不要为了显得有力量而重复同一个结论。
先从对话提炼一份跨平台故事内核，再只写当前指定平台的一个版本。不得生成其他平台版本。
core.visualConcept 只用于后续美术或封面，不得反向主导、增删或改写正文。
```

输出字段：`core` 包含事实、核心判断、情绪、声音特征和视觉概念；`draft` 包含标题、标题来源锚点、正文、标签。视觉概念仅供后续美术使用。

## 3. 写作用途：当前原文

系统会附上主用途、核心观众、兼顾用途和次要观众，然后按主用途选择一条：

| 用途 | 提示词原文 |
| --- | --- |
| 留存（默认分支） | 优先保留真实原话、细节和未完成的感受；不为外部传播强行补冲突、结论或口号。 |
| 礼物 | 先挖掘核心观众与用户之间共同经历、专属物件、关系如何彼此改变，以及想说却没说出口的话；写给这个人，不把私人关系磨成泛泛鸡汤。 |
| 分享 | 先让陌生人快速进入真实处境，再给出值得停留的反差、判断或实用价值；保留用户立场，不把故事改成热点模板。 |
| 介绍／说服 | 先给清楚主张，再用用户说过的项目、行动、结果或判断作证据；优先消除核心观众的真实疑虑。 |
| 创作 | 优先维持人物欲望、世界规则和形式感；不要把创作写成个人经历复盘或营销文案。 |

所有用途随后追加：

```text
无论用途是什么，都从人的基本诉求出发：被看见、被理解、归属、尊严、安全、成长、爱或创造。不要把这些词直接写成口号；让具体经历、关系和选择承载它们。
```

## 4. 平台文风：当前原文

| 平台 | 提示词原文 |
| --- | --- |
| 小红书 | 开头尽快说清真实处境，使用易读短段落，可选少量话题标签。 |
| X | 首句直接给出判断；单条不超过 X 的 280 加权字符，较长内容拆成最多 8 条、逐条编号的 thread。 |
| Instagram | 用视觉感强的短开头进入正文，保持自然语气，可选克制 hashtags。 |
| LinkedIn | 先交代专业语境，再给证据与个人判断，保持清晰的段落节奏。 |
| 朋友圈 | 像对熟人说话一样自然，控制格式和标签，不把分享写成营销稿。 |
| 抖音 / TikTok | 开头先给钩子，句子短而可读，可选少量话题标签。 |

共同规则：适配平台只改变篇幅、段落、开头和标签习惯，不能改变事实、观点、情绪或结论。X 另有无独立标题、最多 8 条、编号与末条标签计入长度等硬要求。

## 5. 标题：当前规则摘要

- 独立写一个标题，不直接截取正文第一句，也不做正文摘要。
- 让陌生人看到真实处境、具体细节、反差或用户判断。
- 优先取原文中的物件、动作、场景、结果、判断或有辨识度的短句。
- 不制造悬念、冲突、承诺、数字、人物、结果或情绪强度。
- 标题须提供同时逐字存在于标题和输入素材中的来源锚点；封面视觉概念不是合法标题素材。
- 建议长度读取 `shared/textTitle.ts` 的平台策略；X 的标题与锚点均为空。

## 6. 正文改写：当前主提示词原文

以下固定正文后还会拼入平台规则与 JSON 输出格式。

```text
你是用户直接指挥的发布稿改写编辑。只改当前平台的一份稿件，先准确执行用户这次提出的语言、节奏和篇幅要求。
不得添加原稿和故事内核中没有的事实；不得偷偷弱化核心观点，也不得把个人表达改成营销话术。
用户要求更克制、更直接或少一点修辞时，保留事实和具体判断即可，不必保留原稿的情绪强度、比喻或所谓“锋芒”。
这类克制改写必须把观点落回具体动作与因果，不要把一种修辞替换成另一种修辞。删除“危险的信号”“背叛”“反噬”“尸体”“物理地基”“存在的根基”“守住……就是守住……”等宏大、拟人或口号式表达，除非用户明确要求保留某一句。
严格保持原稿的事实确定程度和时态：看到、听说、报道、计划、可能等表述，不得升级成已经确认、已经执行或必然发生。
事实边界优先于用户要求；用户指令不得改变、捏造或升级事实。标题由独立标题操作管理，本次改写不得重新创作标题：非 X 的 draft.title 与 draft.titleAnchor 都原样复制 currentDraft.title，X 的两项都返回空字符串。
用户未明确要求修改标签时，draft.tags 必须逐项原样复制 currentDraft.tags。
不要使用 Markdown 粗体符号。只有用户明确要求时才使用 emoji、网络热词或夸张语气。
```

## 7. 旁白文字目前从哪里来

发布稿转故事版的 `server/services/publishingVideoStoryboard.ts` 明确规定：`scriptText` 是视觉剧本，旁白文字由系统直接继承文字稿原文。

`shared/publishingVideoStoryboard.ts` 将段落原文写入该段第一镜的 `voiceText`，其余镜头为空。正式旁白生成由 `server/services/storyNarration.ts` 读取字幕 cue 的文字。因此，“重新写一版适合朗读的旁白”目前不是这里的一套独立文案提示词。若后续希望增加口语化改写，应另行明确是否保留原文、采用方式以及字幕如何同步。

## 8. 建议逐项讨论的调整点（尚未应用）

1. **默认表达是否过度偏向评论文章。** 首次生成总要求“用户为什么不同意”，但留存、礼物和创作不一定存在反对意见。可讨论将其限定在确实有批评或异议的素材中。
2. **是否需要统一的情绪框架。** “无论用途”都列举基本诉求，可能诱导原文没有的情绪解释；礼物分支的“想说却没说出口的话”也应区分用户已表达内容与模型猜测。
3. **文风限制应有多强。** 目前“克制、直接”和禁用表达占比很高，可根据用户想保留的语言个性，决定哪些是默认偏好、哪些仅在明确要求克制时生效。
4. **改写与平台规则的优先次序。** 用户要求降低情绪强度，但通用平台规则说“不能改变情绪”，存在措辞上的张力；需要区分情绪立场与表达强度。
5. **文风修复的标题规则。** 主改写要求复制标题，后续文风修复却重新拼入标题创作规则。是否造成最终标题变化还需结合校验与回填路径验证，这里仅记录提示词不一致。
6. **旁白是否需要独立版本。** 当前继承文字稿；单独改成口语稿属于新增写作步骤，需要明确字数、口吻、时长及原文保留方式。

功能账本 `publishing-workspace` 当前状态为 `working`，同时仍列出文字操作 DOM 交互、冲突恢复与刷新验证的已知缺口。平台稿隔离、人工标题保护、Story/版本/修订作用域和同操作重复请求不重复调用模型是已有约束。
