# 功能生命账本

这里记录产品现在真正拥有的能力，不替代 `docs/brainstorms/` 的需求背景或
`docs/plans/` 的实现决策。Agent 在改相关代码前先读
`feature-ledger.json`，完成工作后更新所属功能卡的证据、缺口和历史。

## 按需读取

`pnpm feature:context memorySpace` 搜索名称、ID、用户价值、入口和权威代码路径；多词按同时匹配处理。不传关键词列出全部功能的 ID、状态和名称。

`pnpm feature:context --id memory-bookshelf-people` 输出当前功能卡，保留全部约束、依赖、缺口与证据，只省略 `history`。它直接读取本目录原账本，不维护第二份索引。需要历史决策时再读取原卡的 `history`；没有搜索结果不代表可以删除功能，应换关键词或查看完整列表。

## 状态

- `working`：真实入口和自动化证据均已通过。
- `partial`：部分链路可用，仍有明确缺口。
- `broken`：用户入口存在，但已复现无法完成主要目标。
- `observing`：代码已经存在，正在逐项验收，尚不宣称完整可用。
- `planned`：只有经过确认的需求或计划，还没有可运行实现。
- `superseded`：历史能力已被另一张功能卡替代，仅保留来路。

`working` 必须至少引用一个测试或可重复执行的验证命令。页面、类型、计划文档
和一次人工演示都不能单独证明功能可运行。

## Agent 开工闸门

1. 搜索与任务相关的功能卡，先向用户报告当前能力、约束和已知缺口。
2. 若工作可能覆盖、削弱、替换或删除已登记能力，停止修改，列出受影响功能与
   取舍，等待用户明确批准。
3. 新增持久用户能力时建立功能卡；修复、重构和性能优化只追加到所属功能的
   `history`，不要制造同级噪音卡。
4. 结束前更新状态、代码所有权、测试证据、依赖和缺口，并运行
   `pnpm feature:validate`。

## 字段说明

- `entryPoints`：用户或 Agent 实际触发能力的入口。
- `owners`：该能力的权威实现位置，不是所有调用方。
- `evidence`：测试、验证命令或调查文档；`working` 需要可执行证据。
- `invariants`：后续修改不可静默破坏的行为。
- `dependencies`：能力依赖的其他功能卡 ID。
- `replaces` / `replacedBy`：明确替代关系，禁止循环。
- `knownGaps`：已知但尚未解决的运行缺口或验证空白。
- `history`：功能、修复、重构、决策和验收记录。
