# 目标与已确认决定

作者将一个链接或二维码发给信任的人。收件人打开后，能够以这段故事为起点继续聊、改写和生成自己的作品，不必重新解释原故事的背景。

用户已明确：**对收到链接的人来说，这是他自己创造的一个新故事。** 因此创建独立 Story，归收件人所有；原作者的故事不变，双方之后独立演进。二维码只是同一分享链接的另一种呈现。

## 已确认的访问方式

用户选择：**持有链接即可查看；登录后才能创建、改写和保存自己的故事。**
首版交付可复制链接，二维码为同一地址的可选呈现，不引入第三方二维码服务。

## 首版操作

1. 作者在当前故事里点击「邀请他改写」。预览直接使用编辑器当前可见的标题、正文和标签；其他背景读取已保存的故事。分享无需额外调用文风评估或把草稿应用回原作。
2. 小窗口展示即将分享的标题、正文与故事上下文范围；作者确认后得到可复制链接。首版只交付链接，二维码暂不实现。
3. 收件人打开链接，先看到分享的故事与「以此开始我的故事」。打开链接本身不创建故事，也不调用付费模型。
4. 按确认后的访问规则建立归收件人所有的新 Story，进入现有聊天与文字工作区。原文作为可编辑起点，原故事上下文作为明确标注来源的参考。
5. 收件人继续表达自己的想法，复用现有聊天、改写、配图和导出能力。费用和算力归收件人自己的账号，不能沿用作者凭据或额度。
6. 作者可停止分享。停止后不再允许通过该链接查看或创建副本；此前已经创建的独立故事不被撤回或删除，界面需要明确说明这一点。

## 上下文范围

分享的是当前故事的授权快照，不是整个账号或原始数据库对象。建议使用显式字段白名单：

| 内容 | 首版处理 |
| --- | --- |
| 当前标题、正文、主题、故事摘要 | 纳入分享预览和新故事起点 |
| 当前故事的事实/素材卡、人物关系、表达意图 | 作为有来源标识的故事参考，不能冒称收件人自己的经历 |
| 当前故事的聊天文字 | 默认不纳入；作者勾选并预览确认后纳入，保留发言身份，不能伪装成收件人的历史发言 |
| 原作者的跨故事记忆、个人文风学习、其他故事 | 不读取、不共享、不继承 |
| 原始上传附件、图片/声音/视频资产、镜头和时间线 | 不直接复制私有资产ID或私有URL；首版以文字上下文为主，若需要继承媒体，另做明确授权及资产复制 |
| 任务回执、操作token、计费状态、账号信息、内部提示词 | 不进入快照 |

不额外调用模型来“总结后再分享”，避免成本、等待和上下文误写。文字过长时应提示范围限制，不静默截断。来源内容保持可查看，后续提示组装复用现有上下文预算。

## 版本与归属

- 一次分享固定到作者确认时的快照。作者后续改稿不会悄悄改变已经发出的内容。
- 新 Story 生成新的ID与revision，所有后续读写仍校验新 storyId + 收件人 userId。
- 共享上下文作为引用资料；不能注入系统权限指令，也不能进入收件人的个人记忆、偏好学习或“本人经历”证据。
- 原发布版本、已完成成品、付费任务及原素材引用不整包克隆。新故事从独立文字草稿开始，按现有工作区合同初始化。
- 同一收件人的重复点击/请求重试复用创建回执，不能产生多个意外副本；明确再次创作的操作与网络重试分开。

## 链接边界

- 使用不可枚举的随机token，存储校验值；禁止以可猜测storyId充当授权。
- 普通故事查询、保存、素材接口继续按归属校验，绝不为分享放宽为公开接口。公开入口只读取经过筛选的分享快照。
- 分享创建/停止仅作者可操作。无效、撤销、原故事已删除等情况展示统一不可用状态，不泄露作者其他内容；首版无自动过期时间。
- 链接持有者可继续转发这一事实应在分享窗口明确。若用户选择指定账号，按实际账号校验，不能只隐藏按钮。
- 分享页不建立索引，不加载会收到token的外部分析/二维码服务；二维码应在本地生成，不能把私人链接发给第三方二维码网站。
- localhost链接只能本机使用。对外可用链接必须基于实际部署域名；本地开发通过仅本机验收后仍需公网、另一账号/设备复验，不能把本地成功称作对外可用。

## 现有能力与实现落点

已核对的已有能力：

- `server/repositories/stories.ts`、`server/routers/storyAgent.ts`：按用户归属创建/读取故事，已有聊天和新故事进入路径。
- `shared/storyContract.ts`：故事基础结构；其中含可扩展记录，不能直接把整个body作为分享快照。
- `client/src/features/storyAgent/chatStoryContext.ts`：当前故事/发布稿上下文描述，可作为接入参考；不能把已有600字摘要误当完整继承。
- `client/src/app/router/AppRouter.tsx`：现有编辑器和登录路由；登录返回目前仅允许`/m`，需为分享路径增加严格允许规则，不能开放任意returnTo。
- `server/routers/shiguangStoryAccess.ts`与`shared/storyShareCard.ts`属于另一套拾光权威故事/图片卡协议，不是本次编辑工作台Story的链接复制，不能直接混用其accessId。
- 功能账本`story-ownership`为working，原归属校验不可削弱；`publishing-workspace`可复用；`publishing-versions`为observing，不能把新故事误建为原故事的新成品版本。

计划新增最小三层：

1. **分享快照与持久化**：一个专属服务/仓库支持本地和SQL模式，保存快照、授权校验、撤销状态与创建回执。不建立通用协作权限框架。
2. **创建、读取、承接、停止分享接口**：作者操作需登录且校验归属；接收者查看无需登录，创建自己的故事必须登录。承接成功进入既有Story，后续不用第二套编辑器。
3. **单一分享入口和接收页**：复制链接为第一交付，二维码复用该链接；接收页只需预览与开始按钮，兼容手机。

## 验收

- 作者A创建分享；用户B打开并创建新故事，继承授权文字上下文，继续聊天能引用原背景。
- B修改标题/正文和生成内容，A的故事内容、revision、素材均不变；用户C不能读取B的副本。
- 来源聊天不会成为B的个人记忆或伪造的B历史发言；账号资料和其他故事不在响应中。
- 分享内容固定；A后续修改不改变旧链接内容。停止分享后新访问/创建被拒绝，B已完成的独立故事保留。
- 无效token、删除源故事、重复点击、并发创建、写盘失败及登录返回均有服务层/接口测试。
- 创建新故事与回执持久化的一致性有测试；失败不能留下可被重复领取的孤儿副本。
- 浏览器验证作者分享→接收预览→登录/承接→进入新故事→继续改写；首版不要求二维码。
- 功能未通过入口和可执行测试前，账本状态不能标working。
